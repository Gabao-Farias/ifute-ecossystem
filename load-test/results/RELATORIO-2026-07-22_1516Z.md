# Relatório de Teste de Carga — Plataforma iFute

**Data:** 2026-07-22 · **Janela:** 15:12–16:25 UTC (12:12–13:25 BRT)
**Alvo:** `https://api.ifute.com.br` (produção) · **Escopo:** caminho de leitura do app mobile
**Ferramenta:** k6 v2.1.0 (executor `ramping-arrival-rate`) · gerador rodando no Brasil (RTT transatlântico ~187ms até a VPS na OVH Canadá)

> **Contexto:** teste autorizado em produção pois a plataforma hoje só atende o time interno (sem usuários finais). Todas as alterações temporárias em prod (release do core com bypass de rate limit, exceção no nginx) foram **revertidas ao fim** — prod voltou a rodar `ifute-core-simple:0.3.1` com todas as proteções ativas.

---

## TL;DR

- **A infraestrutura NÃO é o gargalo hoje. O gargalo é o processo Node do backend, que é single-thread e satura ~1 de 4 CPUs — deixando 3 cores ociosos sob carga.**
- Postgres, RAM e rede têm folga enorme: no pico, apenas **16 de 100** conexões do Postgres em uso e **~2 GB de RAM livres**.
- Teto sustentável estimado (com boa latência): **~100–150 req/s agregados** para os endpoints de leitura. Acima disso a latência despenca de ~190 ms para **6–20+ segundos**.
- O throttle do nginx (`limit_req` 10 r/s por IP) e o do app (50 req/min por IP) são **proteções por-cliente** e **não** limitam a capacidade agregada — devem ser mantidos.
- **Maior alavanca (baixo esforço, alto impacto): rodar o core em múltiplos processos/réplicas** (cluster/PM2/réplicas atrás do nginx) para usar os 4 cores → potencial de **~3–4× throughput**.

## Ambiente testado

| Recurso | Valor |
|---|---|
| VPS | OVH, AlmaLinux, **4 vCPUs**, **7,5 GB RAM** (~2,1 GB livres em idle) |
| Backend | `ifute-core-simple` (Node 20, Express, TypeORM), container com `mem_limit=512m` |
| Banco | PostgreSQL 16.4, `max_connections=100`, mesmo host (compartilhado) |
| Proxy | nginx, `limit_req` 10 r/s por IP (burst 20) na API |
| Rate limit do app | 50 req/min por IP (mobile) |

Endpoints exercitados (mix ponderado): `GET /mobile/public/place/discover` (45%), `GET /mobile/public/place/?place_id=` (40%), `GET /mobile/public/place/city` (10%). O `discover` é o mais pesado (query geo + montagem de disponibilidade). `cost-breakdown` (privado) ficou de fora (sem JWT de teste).

## Run 1 — proteções ativas → revela o teto do nginx (não da infra)

Rampa 25→300 req/s, 11m30s, com o rate limit do **app** contornado (header secreto) mas o `limit_req` do **nginx** ainda ativo.

| Métrica | Valor |
|---|---|
| Requests totais | 97.918 (~142/s oferecidos) |
| **Sucessos (2xx)** | **6.908 → ~10/s** |
| Falhas (não-2xx) | 92,9% (503 do nginx) |
| Latência p95 | 202 ms (dominada por RTT; a maioria são 503 rápidos) |
| Host no pico | core CPU ≤27%, load ≤1,5, **pg conns 6–8** — **box ocioso** |

**Leitura:** os ~10 sucessos/s batem **exatamente** com o `rate=10r/s` do nginx. De um único IP, o nginx capa qualquer cliente em 10 r/s e o servidor **nem sente**. Esse é o teto *por-cliente*, não o da infra. Para medir o servidor foi preciso remover também esse limite (Run 2).

### Métricas do host durante o Run 2 (correlação)

| Instante (UTC) | core CPU | pg CPU | pg conns | load(1m) | RAM livre |
|---|---|---|---|---|---|
| idle (pré) | 0% | 0% | 6 | 0,08 | 2,1 GB |
| +30s | **122%** | 38% | 13 | 0,79 | 2,09 GB |
| +2min | **116%** | 40% | 15 | 1,83 | 2,03 GB |
| +5min | **125%** | 41% | 16 | 2,37 | 2,01 GB |

**O que satura:** o container do core fica preso em **~108–134% de CPU** (≈1,2 de 4 cores) durante toda a carga. Como o Node é **single-thread**, ele estoura ~1 core e **não usa os outros 3**. Em paralelo:
- **Postgres**: CPU 40–57%, **conns nunca passam de 16/100**, queries ativas 1–3 → **muita folga**.
- **RAM**: ~2 GB livres o tempo todo; core usa ~13% do seu limite de 512 MB → **sem pressão**.
- **Host load**: pico ~3,5 (de 4) — o *host* tem folga, mas o *processo* não consegue aproveitá-la.

### Onde fica o joelho

- **~100 req/s** (30s de teste, 55 VUs): ainda saudável.
- **~300 req/s** (60s de teste): já colapsado — VUs saltaram para 1.145 e a latência foi para segundos.

## Diagnóstico

```
Camadas e seus tetos (por-IP → agregado):
  nginx limit_req .......... 10 req/s por IP      (proteção por cliente)
  app rate limit ........... 50 req/min por IP    (proteção por cliente)
  ── removidos os dois ──
  core (Node single-thread)  ~100–150 req/s        ← TETO REAL DA INFRA
  Postgres (100 conns) ..... >> não alcançado      (16/100 no pico)
  RAM / disco .............. >> não alcançado
```

O backend é um único processo Node por container. Sob carga ele satura **um** core de CPU e a fila de eventos engorda, disparando a latência. Os outros 3 cores, o Postgres e a RAM ficam ociosos. **Escalar o número de processos do core é o caminho — não trocar de servidor.**

## Capacidade estimada (hoje)

| Cenário | Capacidade |
|---|---|
| Por cliente (config atual de prod) | 10 req/s (nginx) — mais que suficiente por usuário |
| Agregada, boa latência (~<300 ms server-side) | **~100–150 req/s** |
| Agregada, ponto de colapso | ~200–300 req/s (latência → segundos) |

> Traduzindo para usuários: se cada usuário ativo faz ~1 request a cada poucos segundos, o teto atual comporta na ordem de **algumas centenas a ~1–2 mil usuários simultâneos** navegando — mas isso vira **~4×** apenas usando os cores ociosos.

---

## Recomendações (priorizadas)

1. **Rodar o core em múltiplos processos para usar os 4 cores.** Opções, do mais simples ao mais robusto: Node `cluster`, PM2 em modo cluster, ou N réplicas do container com o nginx balanceando o upstream. **Ganho esperado ~3–4×** com esforço baixo. É a ação de maior impacto.
2. **Ao escalar, ajustar o `mem_limit` do core** (512 MB é apertado para N workers; hoje usa ~65 MB).
3. **Dimensionar o pool do TypeORM por worker** para não estourar as 100 conexões do Postgres (N workers × pool ≤ 100 com margem). Hoje o pool mal é usado (16 conns).
4. **Cachear as respostas de leitura** (`discover`/detalhes mudam pouco) — via cache HTTP/CDN ou cache curto no app. Reduz drasticamente a carga por-core do endpoint mais pesado.
5. **Manter** o `limit_req` (10 r/s/IP) e o rate limit do app (50/min/IP) — são proteções por-cliente e não limitam a capacidade agregada.
6. Depois do item 1, **re-testar** para achar o novo teto (provavelmente o Postgres ou a query do `discover`).

## Ressalvas e limitações

- **Só o caminho de leitura público foi testado.** Escrita/pagamento (criação de order → Asaas) **não** foi exercitado sob carga — envolve dinheiro real e deve ser testado em sandbox/local.
- **Latência absoluta inflada por RTT** transatlântico (~187 ms Brasil→Canadá). O **teto de throughput (req/s) é server-bound e válido**; os números de latência de um usuário real dependerão da rede dele.
- Teste de **IP único com proteções desabilitadas temporariamente** (revertidas). Mede a **capacidade agregada do servidor**, não o comportamento real multi-IP (onde o `limit_req` protege por cliente).
- Nenhuma migração de banco envolvida; nenhum dado de produção alterado.
